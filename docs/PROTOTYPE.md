# 超节点计算卡故障风险预测 Demo

本 demo 基于 `uce_risk` 算法（按字段自适应、AI + 规则混合、多时间窗风险模型）和当前可用的开源数据集，演示完整链路：

**自动采集 → 自动处理成模型输入 → 定时扫描未来 1 小时 / 4 小时 / 24 小时风险 → 发现问题节点和计算卡 → 故障树自动归因 → 历史回溯验证有效性。**

界面一律使用"计算卡"，故障一律用与厂商无关的故障原因（`configs/error_taxonomy.json`）表示，不出现厂商错误码。

## 运行

```powershell
python supernode\build.py          # 离线构建：约 10–20 分钟，--quick 为不调参的快速版
python supernode\server.py         # 浏览器打开 http://127.0.0.1:8765（环境变量 PORT 可改端口）
```

构建产物在 `D:\gpu_data\supernode\`，配置在 `supernode/config.json`（拓扑、时间窗、扫描周期、采集源、端口）。

## 监测对象

一个超节点 `SN-01`：

- 16 个机柜（R01–R16），每个机柜 8 个计算节点，每个节点 8 张计算卡，共 1,024 张；
- 命名为 `R03-N5-C2`（机柜-节点-卡）。

## 架构

```
sources.py   采集：本机探测（管理工具 / 数据中心管理工具 / 遥测导出端点 / 内核日志 / 采集器目录）
             + LocalCollector（本机实时采集）+ Replayer（开源数据回放，按采集器 JSONL 格式写入缓冲目录）
ingest.py    处理：采集器 JSONL → 与厂商无关的事件表和遥测表 → uce_risk.inputs.from_tables（按字段自动生成模型输入）
engine.py    调度：监测时钟；每个周期依次执行采集、解析、扫描（1/4/24 小时风险）、故障树归因；提供查询接口
policy.py    报警策略（高风险 / 关注阈值）与有效性评估（含与规则同等告警量的对比）
fta.py       故障树：5 个或门、20 个基本事件；权重为 P(24 小时内 UCE | 事件)，在训练数据上估计
build.py     离线构建：遥测库、选卡、两组模型训练、故障树权重、历史逐小时扫描、有效性
server.py    Flask 接口；static/ 为不依赖外部库的单页前端
```

### 数据来源与映射

| 数据 | 来源 | 覆盖 |
|---|---|---|
| 错误日志（逐卡、真实时间） | OLCF Summit 公开错误日志（`dataset/failures.csv`） | 973 张卡。回放期内发生过不可纠正错误的卡（41 张）和有硬件错误的卡（150 张）全部纳入，其余随机抽取 |
| 地址级显存 RAS 日志 | Calchas 公开 HBM 错误日志（CE / UER / UEO，含 stack/SID/PC/BG/bank/行/列） | 机柜 R16 的 51 张卡，时间整体平移到回放期 |
| 遥测与作业日志 | Summit 工件中 2020-01 的真实 10 秒遥测（每卡功率、核心温度、显存温度，作业分配号），降采样为 5 分钟 | 全部 1,024 张卡。各节点每天回放一个真实的"节点-日"剖面 |
| 本机实时采集 | 本机管理工具（如有） | 本机计算卡，真实时间 |

**按字段适配的体现**：有地址级显存日志的 51 张卡，输入字段多了 CE 和地址层级，`from_tables` 自动启用"可纠正错误计数 + 空间故障模式"模块，使用"显存 RAS 模型"。其余卡只有错误事件，使用"运行日志模型"。两组卡在同一个监测周期里同时扫描。

### 模型与阈值

- **运行日志模型**：在 Summit 全部 28,524 张卡 2021-07 之前的数据上训练，2021-04 之后为验证期。
- **显存 RAS 模型**：在 Calchas 2023 年之前的数据上训练。
- 两者都是 `UCERiskPredictor`：LightGBM 分段风险模型 + 规则评分卡 + 单调约束，3 个种子装袋，验证期正样本足够时自动调参。
- **报警阈值**（`policy.py`）：
  - 24 小时：高风险 = 验证期 F1 最优阈值；关注 = 验证期 1% 无故障卡误报阈值（不高于高风险阈值的 1/3）。
  - 1 小时 / 4 小时：验证期正样本太少，直接拟合的阈值不稳定，所以按"与 24 小时相同的告警比例"取分位数。只用模型输出，不用标签。

### 故障树

| 或门 | 基本事件 |
|---|---|
| 显存子系统故障 | 近期不可纠正错误（复发）、多次不可纠正错误、页退役 / 行重映射、页退役失败、可纠正错误率过高、可纠正错误突发、行 / 列结构性故障、Bank 级故障、巡检发现不可纠正错误 |
| 芯片本体 / 互连故障 | 掉卡、片间互连链路错误、片上管理控制器告警 / 停机 |
| 热与供电应力 | 显存温度偏高、核心温度偏高、功率剧烈波动、节点整体散热异常（来自实时遥测，相对全超节点的 z 分数） |
| 节点 / 环境共因 | 同节点其他卡近期不可纠正错误、同节点错误事件频发 |
| 软件 / 作业诱发 | 应用类错误频发、驱动 / 固件异常 |

- 基本事件的权重 p = P(24 小时内不可纠正错误 | 该事件出现)，在训练数据上估计，同时给出相对风险 RR。
- 或门概率 = 1 − Π(1 − p)；故障类别取概率最大的门，根因取该门中 p 最大的基本事件。
- 遥测类基本事件没有带标签的历史数据，采用专家先验 RR × 基线概率，并在界面上注明"专家先验"。

## 集群实时采集（A100 等计算节点）

页面顶部可以在两种数据源之间切换：**开源数据回放**和**集群实时采集**。

### 部署

```bash
# 监测服务器
python supernode/server.py

# 每个计算节点（如 8 卡 A100 服务器）；需要 Python ≥ 3.8 和厂商管理工具，无第三方依赖
curl -fsSL http://<监测服务器>:8765/agent/install.sh | sudo bash     # 一键安装为 systemd 服务（Agent 由监测服务提供）
python supernode/agent.py --server http://<监测服务器>:8765    # 或前台运行
python supernode/agent.py --print-capabilities        # 只查看本机能采集什么
```

- Ubuntu 22.04 内网的正式部署：使用发布包中的 `sudo bash install.sh`（离线、注册系统服务、打印 `http://<IP>:<端口>`），见发布包 `docs/DEPLOY.md` §0。
- 监测服务器所在机器如果装有计算卡，会自动启动一个本机 Agent，作为一个节点接入。
- 节点在拓扑中的位置：
  - 默认按接入顺序分配；
  - 也可以在 `D:\gpu_data\supernode\cluster\inventory.json` 中指定，例如 `{"hostname": "R03-N5"}`；
  - 分配结果保存在 `hosts.json`，服务重启后位置不变。

### 采集能力自动判定

Agent 启动时逐项探测本机能采集的内容，结果上报给服务端，显示在"数据采集与处理"页：

| 探测内容 | 方式 |
|---|---|
| 指标字段 | 先查驱动支持的查询字段，再实测每张卡：驱动列出但设备返回 N/A 的字段记为不可用（例如消费级卡没有 ECC） |
| 指标分组 | 温度、功率、时钟与利用率、可纠正 / 不可纠正错误计数、行重映射计数与状态、重映射资源余量、页退役、降频原因、PCIe、恢复动作、ECC 模式、片上 SRAM 错误明细 |
| 旁路数据源 | 内核错误日志（journalctl / dmesg）、设备事件监听、片间互连错误 |

服务端根据这些字段判定能构建哪些模型输入：

| 有哪些数据 | 判定结果 |
|---|---|
| 遥测 + 可纠正错误统计（+ 错误事件） | 方案 3 |
| 遥测 + 错误事件 | 方案 1 |
| 只有可纠正错误统计 | 方案 2 |
| 只有遥测 | 只能做热 / 供电归因，不给出有效的故障风险 |

然后为每张卡选择模型。实测结果：本机的消费级卡被判定为"仅遥测"；A100 类节点（模拟）被判定为"方案 3 + 错误事件"。

### 采集到的数据如何用于分析预测

Agent 复用 `collectors/gpu_ecc` 采集器。采集器的输出经 `ingest.records_to_tables` 转换后，送入同一套按字段适配的输入层和模型：

| 采集器输出 | 转换结果 |
|---|---|
| 温度 / 功率样本 | 遥测（热 / 供电类故障树事件，详情页遥测曲线） |
| 可纠正错误计数的增量 | 可纠正错误记录（带计数） |
| 不可纠正错误计数的增量、内核日志中的不可纠正错误 | 不可纠正错误标签与历史 |
| 行重映射 / 页退役计数增加 | "页退役 / 行重映射"事件 |
| 重映射失败标志 | "页退役失败"事件 |
| 卡消失 | "掉卡"事件 |
| 内核错误日志 | 按 `configs/error_taxonomy.json` 映射为故障原因 |

### 采集频率与存储

- **采集频率**：在页面上设置，默认 5 分钟，可选 1–60 分钟或自定义秒数。保存后，各节点 Agent 在 1 分钟内拉取并生效。
  - 较慢的档位按比例放大：错误明细和互连计数为 2 倍间隔，`-q` 解析为 ≥5 分钟，原文归档为 ≥12 倍间隔。
  - 同一频率也是集群模式的扫描周期。
  - 内核错误日志始终实时读取，不受频率影响。
- **存储**：
  - 页面按实测的单条记录大小估算每天和保留期内的存储量。
  - 实测一条 A100 类样本约 1 KB。5 分钟频率下，1,024 张卡约 290 MB/天；30 秒频率下约 3.1 GB/天。
  - 数据保留天数可设置（默认 30 天），服务端每小时清理过期的原始记录。Agent 本地的数据同样按保留期清理。
- **可靠性**：
  - 服务端暂时不可达时，数据留在节点本地磁盘，恢复后从断点续传。
  - 服务重启后，从磁盘上的原始记录重建内存状态，并保持节点位置不变。

### 测试情况

本机没有 A100，测试方式如下：

1. 本机的消费级卡作为真实节点接入，验证能力判定和遥测采集；
2. `agent.py --simulate N` 启动 N 个模拟的 8 卡节点。它们使用与 A100 相同的字段集，产生漂移的温度和功率、可纠正错误计数、偶发的行重映射和不可纠正错误，用来验证"注册 → 推送 → 转换 → 扫描 → 告警 → 归因 → 频率下发 → 重启恢复"的完整链路；
3. 自动化测试 `tests/test_cluster_mode.py`。

接入真实 A100 集群时，需要在节点上确认以下两点，脚本已兼容，但本次没有在真实 A100 上验证：

- 内核日志读权限：需要 root，或将运行用户加入 `systemd-journal` 组；
- 行重映射字段。

## 需要说明的地方

1. **故障密度高于真实集群**：为便于演示，选卡时纳入了回放期内发生过故障的设备。
2. **遥测与错误日志不是同一批设备、同一时间段**：遥测来自另一个时间段（2020-01）的真实剖面，用于展示采集链路和热 / 供电类归因。模型训练没有使用遥测时间序列，因为公开数据中没有同时覆盖故障发生前的遥测和故障标签。
3. **首次故障难以预测**：在回溯期，算法主要抓到的是复发和短期内快速恶化的设备。有效性页面分别给出了首次和复发的召回。
4. **接入真实集群**：采集器 `collectors/gpu_ecc` 的输出与本 demo 的缓冲格式相同，`ingest.records_to_tables` 可以直接解析。真实接入还需要补充两件事：
   - 主机 / 卡到"机柜-节点-卡"的映射（资产表）；
   - 在 `engine._collect` 中把回放替换为读取采集器目录。

   本 demo 还没有实现这一步。

# BD 现网数据适配：由 CE 预测 1 / 4 / 24 小时内的 UCE 风险

| 项目 | 内容 |
|---|---|
| 适配代码 | `uce_risk/bd.py`（输入适配、第三张 metric 表、标签、事件与遥测特征）；模型沿用 `uce_risk` 的 AI + 规则混合分段风险模型 |
| 命令行 | `python -m uce_risk.cli bd-table / bd-describe / bd-train / bd-predict` |
| 指标用法清单 | `docs/BD_METRIC_USAGE.csv`（30 台机器清单中的 101 个指标逐个说明进入模型的方式） |
| 模拟数据与评测 | 开发工程的 `experiments/bd_sample/`：`synth.py` 生成模拟的三张表（输出在 `dataset/real_sample/generated/`），`run.py` 评测（结果在 `results/`），报告 `REPORT.md`。这些脚本、数据和报告不随发布包提供，结果摘要见第 7 节 |
| 测试 | `tests/test_bd_adapter.py` |

> 重要说明：现网样例只有 4 行遥测和 3 行工单，不足以训练和评测。本文的模型结果都来自**按现网表结构生成的模拟数据**，

## 1. 三张输入表

| 表 | 对应的现网表 | 粒度 | 在模型中的作用 |
|---|---|---|---|
| 工单表 | `ste_data.seed_karl_event_by_date`（SEED 事件，样例 `工单样例.xlsx`，29 列） | 一个事件一行（同一 event_id 可能多次上报） | UCE 标签的确认与精确时间；非 UCE 故障（如 NodeNotReady）作为整机事件 |
| 遥测表 | `ste_data.sysaiops_sndc_offline_dwd`（窄表，样例 `遥测数据样例.csv`，26 列） | 一个指标值一行：timestamp、uuid、维度列、tag(JSON)、metric、value | 卡的维度与拓扑（uuid → 主机、ipv4、卡号、托盘、机柜、超节点域）；精确到秒的驱动错误码；没有宽表时由它生成第三张表 |
| metric 表（第三张表） | 下游宽表 `ste_data.sysaiops_dcgm_sndc_metrics` 未落表，由遥测表生成 | **1 分钟**一行：timestamp（分钟起点，UTC 秒）、uuid、101 个指标列、date、hour | CE 流、UCE 证据、指标状态变化事件、遥测特征 |

关联键：metric 表与遥测表用 **uuid** 关联；工单表用 **ipv4（缺失时用 ip）** 关联到遥测表中的主机，再落到该主机的各张卡。
现网样例中 date / hour 分区是 UTC（timestamp 1788771381 = 2026-09-07 08:56:21 UTC，hour=08）。

### 1.1 第三张 metric 表的生成规则（`bd.metric_table` / `bd-table`）

1. 每行遥测按 `timestamp // 60 * 60` 落到分钟；以 **uuid + 分钟** 为一行，`metric` 的取值成为列名，`value` 为单元格。
2. 一分钟内有多次采样（现网已从 5 分钟变为 15 秒）时取**该分钟最后一个值**；驱动错误码（`DCGM_FI_DEV_XID_ERRORS`）取该分钟最后一个**非零**值，
   保证同一分钟内的错误码不会被后续的 0 覆盖。
3. 没有 uuid 的主机级指标（如 `cpu_power_usage_watts`）复制到该主机的每张卡。
4. 列名同时接受采集名（`DCGM_FI_DEV_ECC_SBE_VOL_TOTAL`）和下游宽表的 snake_case 名（`ecc_sbe_vol_total`），统一成采集名。
5. 输出按 `date=YYYYMMDD/part-*.parquet` 分区写出，后续按分区流式读取，内存只与单日数据量有关。

用模拟的 15 秒原始窄表（`遥测数据_15s原始样例.parquet`，4 张卡 × 30 分钟 × 100 个指标）验证：转换结果与 1 分钟表逐格一致（0 个差异）。

## 2. 101 个指标如何进入模型

指标按语义分为静态配置、瞬时量、比例、持久累计计数、易失累计计数（驱动重载后归零）、0/1 状态、位掩码、枚举、错误码等类型
（`bd.CATALOG`），不同类型用不同方式处理。101 个指标中 **93 个直接进入模型**；其余 8 个是冗余量（已用比例已覆盖的
空闲/已用/总量）、静态阈值、恒为 1 的上报标记，以及样本中为空的 IPMI 读数。逐个说明见 `docs/BD_METRIC_USAGE.csv`。

| 用途 | 指标 | 处理方式 |
|---|---|---|
| **CE 流**（`ce__`） | `ECC_SBE_VOL/AGG_TOTAL`、`ECC_SBE_VOL/AGG_SRM` | 计数器增量：易失计数给出时间，遇到变小视为复位；持久计数补上采集缺口和复位期间丢失的增量（两者取包络，不重复计数）。设备内存 CE = 总数 − SRAM（子类 1），SRAM CE 为子类 2 |
| **UCE 标签** | `ECC_DBE_VOL/AGG_TOTAL` 增量、错误码 48/94/95、`UNCORRECTABLE_REMAPPED_ROWS` 增量 | 同一张卡 10 分钟内的证据合并为一条；再用工单确认和校准时间（第 3 节） |
| **内存健康状态**（事件 + 遥测） | 行重映射（可纠正/不可纠正行数、待完成、失败）、bank 备用行可用性直方图（Max/High/Partial/Low/None）、SRAM 超阈值 | 状态升起或计数增加记为事件：`CE_ROW_REMAPPED`、`REMAP_PENDING`、`REMAP_FAILURE`、`SPARE_ROWS_PARTIAL/LOW/EXHAUSTED`、`SRAM_THRESHOLD`；同时作为水平量进入遥测特征（已动用备用行的 bank 数、Low/None 档 bank 数等） |
| **驱动错误码**（事件） | `XID_ERRORS` 中 48/94/95 以外的值 | 映射为与厂商无关的错误原因（如行重映射/页退役、可纠正错误率过高、掉卡、片间链路错误、管理控制器停机）；应用类原因（计算引擎异常、非法访问、任务中止等）标为背景事件 |
| **链路与总线**（事件 + 遥测） | PCIe 代数/宽度及最大值、C2C 状态/功耗状态/错误计数、片间 FEC 直方图、P2P 位图、`DCGM_FI_DEV_COUNT` | PCIe 降级、C2C 断开或出错、高位 FEC 纠错、P2P 互连减少、识别卡数减少记为事件；速率和差值进入遥测特征 |
| **温度与降频**（遥测 + 事件） | 芯片/内存温度及其最高运行、降频阈值，时钟受限原因位掩码，SM/显存/视频频率 | 温度、距阈值余量、频率/最大频率、各降频原因的占比；温度降频、硬件降频升起记为事件 |
| **功率与能量**（遥测） | 平均/瞬时功率、累计能量、SoC I/O 功率、CPU 功率 | 功率、瞬时与平均之差、由能量计数折算的功率（复位处置空） |
| **负载与访存**（遥测） | 利用率、内存读写活动、`PROF_*` 各管线与 SM 活跃度、主机/对端内存缓存命中、BAR1、显存占用、`sdnc_*` 带宽与利用率、CMem 读写计数 | 原值或比例；CMem 计数自动判断是累计量还是区间量（累计量取每分钟增量） |
| **采集与复位**（事件 + 遥测） | 所有行的时间间隔、易失计数和能量计数的回落 | 采集中断 ≥10 分钟记 `COLLECTOR_GAP`，回落记 `DRIVER_RESET`；每 5 分钟的分钟数据完整率 |

不在 30 台清单、但在完整指标目录（BD 数据集 V2，147 个）中的指标（如 `ECC_SBE/DBE_*_DEV`、`PCIE_REPLAY_COUNTER`、
各类 violation 计时、`PSTATE`、功耗上限）出现时也会自动使用；目录外的数值列作为通用遥测特征（`te__x_<名称>`）。

## 3. 标签：什么算一次 UCE

1. **卡上的证据**：双比特计数增加、出现错误码 48 / 94 / 95、不可纠正重映射行数增加，任一满足即可。时间取该分钟末尾（保证只用到“已经发生”的数据）；
   遥测窄表中有精确到秒的错误码记录时用精确时间。
2. **工单确认**：`fault_sub_type` 为 xid_48 / 94 / 95（或含 uncorrectable / double bit）的工单视为 UCE 工单，按 ipv4 找到主机。
   同主机的卡在工单故障时间前 30 分钟至后 2 小时内有证据，即为确认，并把 UCE 时间校准为工单的 `fault_timestamp`
   （采集中断时计数器的跳变要等采集恢复才看到，工单给出真实时间）。
3. **工单找不到卡**（该主机这段时间没有任何卡的证据）：不作为标签，而是记为整机事件 `WO_UCE_UNATTRIBUTED`，放到该主机所有卡上。
4. 同一张卡间隔不超过 1 小时的 UCE 合并为一个“UCE 事件段”；每段标记为首次或复发，分别统计召回。
5. 同一 event_id 的多次上报只算一次；多机事件（`is_aggregated=true`）按 `ips` 展开到每台主机。

在模拟数据上：37 个真实 UCE 全部找回、没有多出的标签；34 张 UCE 工单全部确认，另外 3 个 UCE 没有工单，只靠遥测发现。

## 4. 预测时刻与特征

- **预测时刻**：每张有数据的卡**每小时**打一次分；另外在出现 CE、事件、UCE 的每个 5 分钟末尾加打一次（1 小时窗口需要），
  以及近 30 天活跃卡每天 0 点打一次。所有特征只用预测时刻之前的数据。
- **特征组**（模拟数据上共 468 个；几十台机器时默认只用其中与内存故障直接相关的 109 个，见 5.1 节）：

| 组 | 内容 |
|---|---|
| `ce__` | 1 小时 / 6 小时 / 1 天 / 7 天 / 30 天 / 累计的 CE 数，1 小时相对 1 天的加速度，距首次与最近一次 CE 的时间，CE 活跃小时数与天数，CE 风暴分钟数，设备内存与 SRAM 两个子类的数量与占比 |
| `ev__` | 每种事件在 1 小时 / 1 天 / 7 天 / 30 天 / 累计内的次数及距最近一次的时间（错误原因、内存健康状态变化、链路、降频、复位、采集中断、工单） |
| `te__` | 约 70 个遥测量（5 分钟均值）的近 1 小时均值、近 1 天均值、近 1 天波动、近 1 小时相对日均的变化 |
| `hi__` | 该卡过去的 UCE 次数、事件段数和距上次 UCE 的时间（复发） |
| `nbc__ / nbe__ / nbh__` | 同一主机其他卡的 CE、事件、UCE（托盘级共因） |
| `cf__` | 卡在托盘中的位置（gpu 序号）、托盘号 |

## 5. 模型

沿用 `uce_risk` 已验证的结构（详见 `docs/ALGORITHM.md` 第 3 节）：

1. **分段风险模型**：分别学习 (0,1h]、(1h,4h]、(4h,24h] 三段的条件风险，组合成 P(1h) ≤ P(4h) ≤ P(24h)，三个时间窗的结果天然一致。
2. **AI + 规则混合**：规则评分卡（CE 突增/加速、首次出现 CE、CE 风暴、各类硬件事件、近期 UCE、同节点 UCE、遥测处于前 10% 等）
   给出可解释的报警理由，并作为输入喂给 LightGBM；带领域单调约束（UCE 历史、硬件事件越多风险不会越低），两者在 logit 空间按验证期加权融合。
3. **阈值**：在验证期上确定，默认 `fpr1` 工作点按“验证期内无 UCE 的卡中有 5% 告警”确定（`--fpr` 可调；30 台机器约 120 张卡，
   1% 只相当于 1 张卡，过严），另给出验证期 F1 最优阈值 `valF1`。

### 5.1 小样本配置（`bd.PROFILE`，几十台机器时的默认）

30 台机器只有几十次 UCE。在模拟数据上，用全部 468 个特征训练时，树模型和规则评分卡都拟合了与 UCE 无关的波动（各管线活跃度、
应用错误、片间链路 FEC 等），在 1 / 4 / 24 小时上都输给只用 CE 的模型。因此默认配置为：

| 设置 | 内容 |
|---|---|
| 特征（`bd.COMPACT`，109 个） | CE 组全部（含“每单位内存访问的 CE 数”：CE 只有在访问内存时才会被发现，同样的 CE 数在低负载时意味着更高的真实错误率）、UCE 历史、同主机 UCE / CE；内存健康事件（页退役/重映射及失败、可纠正错误率过高、待完成重映射、备用行 Partial/Low/耗尽、SRAM 超阈值、复位）的 1 天 / 7 天 / 30 天计数和距今时间；内存健康水平（累计 CE/UCE、已重映射行数、待完成/失败标志、各档备用行 bank 数）的近 1 小时均值和变化；芯片/内存温度、内存访问活跃度、利用率、功率的近 1 小时和 1 天均值；分钟数据完整率 |
| 树模型参数（`bd.SMALL_DATA_PARAMS`） | 15 个叶子、每叶至少 100 个样本、每棵树随机用一半特征、较强 L2 正则 |
| 短时间窗（`bd.BURST`、`bd.SHARE`） | 短时间窗的正样本每次训练只有几十个：(0, 1 小时] 风险段只用 CE 突发特征（近 1 / 6 小时 CE 数、每单位内存访问的 CE 数、加速度、风暴分钟数、距上次 CE 的时间）建模，因为“1 小时内就要发生”主要体现为 CE 突发，其他特征在这一段只会拟合噪声；(1, 4 小时] 段复用 24 小时合并模型的排序、按本段事件率缩放（比例风险）；(4, 24 小时] 段使用全部 109 个特征 |

其余指标仍由适配层全部转换和保存（事件表、遥测序列），并在 `bd-describe` 中报告；数据量增大后用
`bd-train --features all`（或 `UCERiskPredictor(include=())`）即可改为全部特征 + 自动调参。各项设置的效果见评测报告的消融表。

## 6. 输出表

`bd.predict(...)` / `bd-predict` 对每张最近 1 小时有数据的卡输出一行（建议按 date / hour 分区落表）：

| 字段 | 说明 |
|---|---|
| timestamp | 预测时刻（UTC 秒） |
| uuid、hostname、ipv4、gpu、rack | 卡与主机维度（取自遥测表） |
| p_1h、p_4h、p_24h | 1 / 4 / 24 小时内发生 UCE 的概率，满足 p_1h ≤ p_4h ≤ p_24h |
| alarm_1h、alarm_4h、alarm_24h | 是否超过该时间窗的告警阈值；告警是嵌套的（预计 1 小时内发生，必然也在 4 小时、24 小时内，因此 alarm_1h 为真时 alarm_4h、alarm_24h 也为真） |
| risk_level | 高（1 小时或 4 小时告警）/ 中（仅 24 小时告警）/ 低 |
| reason、reason_zh | 规则评分卡中贡献最大的触发项及其中文说明，如“近 1 天出现待完成的行重映射”“近 1 小时可纠正错误数很高” |
| date、hour | 分区（UTC） |

## 7. 评测结果（模拟数据）

模拟 30 台机器、35 天、37 次 UCE，按主机分组 5 折交叉验证（每次 UCE 都是样本外预测），告警阈值为验证期无 UCE 的卡 5% 告警：

| 时间窗 | PR-AUC | UCE 事件段召回（首次 / 复发） | 卡级精确率 | 误报卡 | 提前量中位数 |
|---|---|---|---|---|---|
| 1 小时 | 0.073 | 68%（52% / 88%） | 54% | 13 / 131 | 0.9 小时 |
| 4 小时 | 0.141 | 84%（76% / 94%） | 50% | 17 / 131 | 3.5 小时 |
| 24 小时 | 0.326 | 86%（76% / 100%） | 63% | 10 / 131 | 17.7 小时 |

与最好的简单规则（24 小时内 CE ≥ 200）在同等告警量下比较，UCE 事件段召回 65% / 76% / 76% 对 59%，24 小时 F1 0.74 对 0.67；
全部 468 个特征时 24 小时 PR-AUC 只有 0.162。规则基线、时间切分、消融、按故障类型的召回和示例见评测报告 `experiments/bd_sample/REPORT.md`（开发工程中，不随发布包提供）。
这些数字只说明流水线和方法在模拟数据上有效，真实效果要用真实数据重新评估。

## 8. 在真实数据上运行

```powershell
# 1) 遥测窄表 -> 第三张 metric 表（窄表按 date/hour 分区导出，逐个文件转换）
python -m uce_risk.cli bd-table --telemetry D:\bd\遥测\ --out D:\bd\metric_1min\
# 2) 检查识别到的字段、指标覆盖、标签来源与工单确认情况
python -m uce_risk.cli bd-describe --work-orders D:\bd\工单.xlsx --telemetry D:\bd\遥测维度.csv --metrics D:\bd\metric_1min\
# 3) 训练（验证期起点之后的数据用于定阈值和融合权重，之后在全部数据上重训）
python -m uce_risk.cli bd-train --work-orders D:\bd\工单.xlsx --telemetry D:\bd\遥测维度.csv --metrics D:\bd\metric_1min\ --val-start 2026-09-12 --out D:\bd\bd_uce_model.joblib
# 4) 打分（默认数据末尾；--at now 为当前时刻）
python -m uce_risk.cli bd-predict --model D:\bd\bd_uce_model.joblib --work-orders D:\bd\工单.xlsx --telemetry D:\bd\遥测维度.csv --metrics D:\bd\metric_1min\ --out D:\bd\uce_risk.csv
```

- `bd-train` 默认使用小样本配置（`--features compact`，见 5.1 节）；机器数量多、UCE 达到数百次后可改用 `--features all`（全部特征 + Optuna 调参）。
- 遥测窄表全量很大时，`--telemetry` 只需提供维度信息（每张卡每天一行即可，例如筛选 `metric = DCGM_FI_DEV_COUNT`）
  加上全部错误码记录（`metric = DCGM_FI_DEV_XID_ERRORS 且 value > 0`）；指标数值从 metric 表读取。
- 拿到真实数据后建议先看 `bd-describe` 的输出：缺失的 30 台清单指标、计数器类型自动判断结果（CMem）、
  UCE 证据来源构成、工单确认率和找不到卡的工单数，确认数据口径后再训练。
- 真实数据只有约 30 台机器，按主机分组交叉验证（每个 UCE 都有一次样本外预测）比单次时间切分更能反映效果。开发工程中的
  `experiments/bd_sample/run.py`（不随发布包提供）实现了这一评测，可直接用于真实数据：
  `python experiments/bd_sample/run.py --work-orders D:\bd\工单.xlsx --telemetry D:\bd\遥测维度.csv --metrics D:\bd\metric_1min\ --out D:\bd\评测\`；
  真实数据没有模拟器的 `ground_truth.csv`，脚本会跳过标签核对，按故障类型的统计合并为一类（all）。
- 读取 `.xlsx` 工单需要 openpyxl（`pip install openpyxl`，离线包未附带）；也可以把工单导出为 CSV 或 Parquet。
